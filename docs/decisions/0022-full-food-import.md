# 0022 — Full USDA + Ciqual import, matched only by exact generated names (M4)
Date: 2026-10-13 · Status: accepted

**Context:** After 0021 the ~250 hand-picked foods (now 258) matched 201 of the 236 ingredient names our models gave in the 2026-10-12 benchmark, but some matches were wrong ("coconut oil" → desiccated Coconut, "pizza sauce" → Pizza margherita, "red pepper flakes" → Bell pepper), and rarer foods couldn't be picked by hand at all. The raw database names ("Squash, summer, zucchini, includes skin, raw") fuzzy-match far too much to be trusted.
**Decision:** Import every other row of **USDA SR Legacy** (7,078) and **Ciqual 2020** (2,867) into `ingredient` with `curated = false` and the source row id in `ref`. Left out: baby food, USDA's branded/QC/American Indian groups, Ciqual's bottled mineral waters. `scripts/build_catalog.py full <USDA dir> <Ciqual dir>` writes `api/app/nutrition/data/full_foods.csv.gz` (committed, 286 KB); the API seeds it on every start (~2 s, chunked upsert).
- **Matching:** (1) exact name/alias, hand-picked rows first, then imported; (2) fuzzy trigram match over **hand-picked rows only**. Imported rows never match fuzzily.
- **Generated short names** for imported rows: drop parentheses, cooking states and filler ("drained", "without salt", "prepacked"); keep the row only if one or two parts remain ("Oil, coconut" → "coconut oil", "Cheese, swiss" → "swiss cheese"); naive singular/plural. Meat, fish, grains and legumes get the plain name only from a cooked row, everything else from a raw or unqualified one ("cooked okra" vs "okra"). A short name is dropped when two rows of one source make it (USDA wins over Ciqual), or when a hand-picked row already answers it, also with a cooking word in front ("cooked brown rice" stays Brown rice). USDA restaurant/fast-food rows and brand names (KRAFT) get none: searchable, never matched.
- **Search** (`GET /api/ingredients`): hand-picked rows first, then imported ones.
- **Quality list:** `api/tests/test_matching_quality.py` pins all 236 benchmark names to their expected ingredient (or deliberately none: "spoon", "dairy", "seasoning", "fish"). Now 222 match; the 14 misses are generic or not food.
- Foundation Foods left out: ~300 rows that mostly repeat SR Legacy with newer analyses, and many lack the energy value we read.
**Barcode:** `GET /api/barcode/{code}` (8–14 digits) asks Open Food Facts (`/api/v2/product/{code}.json`, User-Agent `FoodBuddy/0.1`) and caches the answer in `off_product`: known products 30 days, unknown codes 1 day, a stale answer when OFF is down (else 503). Energy from `energy-kcal_100g`, else kJ ÷ 4.184; no energy → `per100: null` so the user types the label. No scanner in the app yet (iOS Safari has no `BarcodeDetector`).
**Alternatives:** Fuzzy over everything with a higher threshold (still wrong on long names); generate aliases with the vision model (slow on 2 cores, unreviewable); only grow the hand-picked list (doesn't make rare foods findable).
**Consequences:** Imported rows show their database names in the picker ("Blackberries, raw") and have no price or tuned shelf life (by category). The hand-picked catalog stays the place to fix a food we eat often; adding a row there removes it from the import on the next build. ODbL: OFF data is credited in `data/SOURCES.md` and the API response (`source`).
