# 0018 — Self-hosted open VLM + nutrition-database grounding
Date: 2026-10-04 · Status: proposed (model chosen by the phase-0 benchmark)

**Context:** Plate photo → dish, ingredients, macros, with no running costs and open source preferred. Research (Open-KNEAD 2026, DietAI24) shows decomposing into items and grounding them in a nutrition DB gives auditable, competitive estimates. Portion size is the main error source.
**Decision:** A self-hosted open-weight VLM (default candidate **Qwen3-VL Instruct, Apache-2.0**; Qwen2.5-VL and Gemma 4 as benchmark alternatives) running on **Oracle's CPU** via Ollama (4B by default, 2B if too slow) returns strict JSON: dish + ingredients with grams. Macros are computed from **USDA FoodData Central + ANSES Ciqual + Open Food Facts** (barcodes) imported into Postgres. User corrections are stored and reused as household priors and as an evaluation set. The worker calls any OpenAI-compatible endpoint, with providers tried in order (today just the local Ollama); if none answers, the job waits and the user can enter the meal by hand. No paid or closed APIs (0019). The weekly planner is deterministic, not an LLM. See `docs/design-plan.md` §4.
**Alternatives:** Paid vision APIs such as GPT or Claude (rejected: cost); a Food-101 classifier only (rejected: no ingredients or grams); segmentation models like FoodSAM (deferred: heavy, experimental); the VLM estimating macros directly (rejected as the main path: not explainable or editable).
**Consequences:** Analysis is async with a push notification (CPU inference: tens of seconds to minutes; measured in phase 0). Needs an eval set (Nutrition5k subset + ~30–50 weighed home meals) to pick and re-check the model.
